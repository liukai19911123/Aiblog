现代前端经常从“选择哪个框架”开始讨论，但浏览器本身已经提供了构建小型内容站所需要的大部分能力。

## 页面其实只有三件事

对这个博客来说，应用核心可以压缩为三个动作：

1. 根据 URL 判断当前页面；
2. 获取配置或 Markdown 内容；
3. 把内容渲染到页面中。

Hash 路由让静态托管无需额外的重写规则。`fetch()` 负责读取文章，DOM API 负责交互，CSS 负责所有响应式表现。

## 配置与正文分离

文章列表需要标题、日期、分类和摘要，详情页需要完整正文。把它们分开保存，可以避免为了展示列表而加载所有文章全文。

```text
index.html
css/styles.css
js/config.js
js/app.js
posts/*.md
about.md
```

这套结构有一个重要优点：每个文件都能独立理解。即使半年后回来，也不需要先恢复复杂的构建环境。

## 什么时候应该使用框架

不使用框架并不是原则。如果页面拥有大量共享状态、复杂表单、服务端渲染或多人协作需求，成熟框架能显著降低沟通成本。

> 技术选择的关键不是先进或落后，而是复杂度是否与问题匹配。

对内容为主的个人博客来说，原生技术提供了更直接、更耐久的答案。
